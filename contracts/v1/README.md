# speakiput GUI/backend protocol v1

This is the normative contract between the native GUI and backend. GUI and
backend may be implemented in parallel as long as both conform to this file,
`envelope.schema.json` and the canonical fixtures.

## Transport

Production connections are local and persistent:

- Linux/macOS: Unix domain socket;
- Windows: named pipe;
- tests: in-memory duplex stream.

Each message is UTF-8 JSON framed by a four-byte unsigned big-endian payload
length. The maximum JSON payload is 1 MiB. One connection is full duplex:
requests and responses are correlated while events may arrive at any time.

The first client message must be `client.hello`. No other request is valid
until negotiation succeeds. Both peers must ignore unknown object fields. New
message names or enum values require a capability or a new negotiated protocol
version; they must not be sent speculatively.

## Envelope

Every message contains:

| field | meaning |
|---|---|
| `protocol_version` | negotiated major/minor string; initially `1.0` |
| `message_id` | unique UUID generated by the sender |
| `kind` | `request`, `response` or `event` |
| `name` | stable dotted message name |
| `sent_at` | RFC 3339 UTC timestamp |
| `correlation_id` | required on responses; request's `message_id` |
| `instance_id` | required after hello; identifies this backend process |
| `sequence` | required on events; increasing per backend instance |
| `payload` | message-specific JSON object |
| `error` | response failure object; when present, `payload` is `{}` |

Protocol errors use:

```json
{
  "code": "invalid_state",
  "message": "Recording is not active",
  "retryable": false,
  "details": {}
}
```

Stable error codes are `invalid_argument`, `invalid_state`, `not_found`,
`conflict`, `unavailable`, `permission_denied`, `timeout`, `unsupported`,
`protocol_mismatch` and `internal`.

## Negotiation and recovery

`client.hello` request payload:

```json
{
  "supported_versions": ["1.0"],
  "client": { "name": "speakiput", "version": "0.1.0" },
  "subscriptions": ["state", "session", "transcript", "history", "settings"]
}
```

Its response selects a version and returns `instance_id`, server version,
capabilities and limits. Immediately after hello, the GUI calls `state.get`.
On reconnect it treats that snapshot as authoritative. If `instance_id`
changes, prior event sequences and in-flight requests are invalid.

Events are ordered by `sequence`. A gap means the GUI must request a new
snapshot; v1 does not replay missed events.

## Requests

| name | payload | successful response payload |
|---|---|---|
| `state.get` | `{}` | `StateSnapshot` |
| `recording.start` | `{ language?: string }` | `{ session_id, state }` |
| `recording.stop` | `{ session_id }` | `{ session_id, accepted: true }` |
| `operation.cancel` | `{ session_id?: string }` | `{ accepted: true }` |
| `settings.get` | `{}` | `{ revision, settings }` |
| `settings.replace` | `{ expected_revision, settings }` | `{ revision, settings }` |
| `credentials.put` | `{ credential_id, secret }` | `{ credential_id, stored: true }` |
| `credentials.status` | `{ credential_id }` | `{ credential_id, stored }` |
| `credentials.delete` | `{ credential_id }` | `{ credential_id, stored: false }` |
| `audio_devices.list` | `{}` | `{ devices, selected_id }` |
| `backends.list` | `{}` | `{ transcription, post_processing }` |
| `history.list` | `{ limit, cursor?: string }` | `{ entries, next_cursor? }` |
| `history.clear` | `{}` | `{ cleared: true }` |
| `diagnostics.get` | `{}` | `{ checks, log_path? }` |

`settings.replace` is atomic and uses optimistic concurrency. A stale
`expected_revision` returns `conflict`; the backend never silently overwrites a
newer revision.

## Events

| name | purpose |
|---|---|
| `state.changed` | authoritative state/session transition |
| `recording.level` | optional normalized `0.0..1.0` meter update |
| `transcript.partial` | replaceable live text for a session |
| `transcript.final` | terminal transcript and insertion outcome |
| `session.failed` | terminal failure for an accepted session |
| `settings.changed` | new settings revision, including external changes |
| `history.added` | newly persisted history entry |
| `history.cleared` | history was cleared by any client |
| `backend.health_changed` | model/provider/platform availability changed |

Every accepted `recording.start` must eventually produce exactly one terminal
event: `transcript.final` or `session.failed`. A response acknowledges a
command; asynchronous completion is always represented by events.

## Core data shapes

`StateSnapshot`:

```json
{
  "state": "idle",
  "active_session_id": null,
  "settings_revision": 3,
  "capabilities": ["local_whisper", "history", "keyboard_insertion", "focus_safe_overlay"],
  "health": "ready"
}
```

States are `starting`, `idle`, `recording`, `transcribing`,
`post_processing`, `injecting`, `error` and `shutting_down`. The
`post_processing` state covers both the existing cleanup and optional prompt
rewriting stages.

Capability names in v1 are `local_whisper`, `post_processing`, `prompt_rewrite`, `history`,
`credential_store`, `keyboard_insertion`, `clipboard`, `global_shortcut`,
`focus_safe_overlay`, `tray` and `autostart`. They describe current-session
availability; the GUI keeps unavailable controls visible but disabled.

`transcript.final` payload:

```json
{
  "session_id": "1ecda715-bd79-43b4-b187-4cf859b20001",
  "raw_text": "teste de input por audio",
  "processed_text": "Teste de input por áudio.",
  "output_text": "Teste de input por áudio.",
  "post_processed": true,
  "prompt_rewritten": false,
  "insertion": { "status": "inserted", "method": "keyboard" },
  "transcription_backend": "local-whisper",
  "language": "pt",
  "duration_ms": 3210
}
```

Insertion status is `inserted`, `clipboard`, `skipped` or `failed`. Keeping
When prompt rewriting is enabled, `rewritten_text` contains its result and
`output_text` contains the text actually sent to the target application.
Keeping `raw_text`, `processed_text`, `rewritten_text` and `output_text`
separate makes ASR, cleanup and rewriting problems diagnosable. The
`post_processed` and `prompt_rewritten` flags identify which transformations
were applied.

`settings` v1 is a single validated document:

```json
{
  "schema_version": 1,
  "general": {
    "language": "pt",
    "auto_stop_ms": 1000,
    "history_enabled": true
  },
  "audio": {
    "input_device_id": "default",
    "phrase_silence_ms": 700
  },
  "transcription": {
    "backend_id": "local-whisper",
    "model_id": "large-v3-turbo-q5_0",
    "model_path": "/home/user/.local/share/speakiput/models/ggml-large-v3-turbo-q5_0.bin",
    "prompt": null,
    "vocabulary": [],
    "remove_filler_words": false,
    "filler_words": []
  },
  "post_processing": {
    "enabled": true,
    "prompt_rewrite_enabled": false,
    "backend_id": "openai-compatible",
    "model_id": "gemma-4-26b-no-reasoning",
    "endpoint": "http://127.0.0.1:1234/v1/chat/completions",
    "credential_id": null,
    "instruction": "Correct punctuation without adding content."
  },
  "output": {
    "mode": "keyboard",
    "key_delay_ms": 2
  },
  "shortcut": {
    "record": "Super+Shift+Space"
  },
  "overlay": {
    "enabled": true,
    "show_partial_transcript": true,
    "size": "medium",
    "screen_anchor": "bottom_center"
  }
}
```

Overlay sizes are `small`, `medium` and `large`. Screen anchors combine a
vertical and horizontal region: `top_left`, `top_center`, `top_right`,
`center_left`, `center`, `center_right`, `bottom_left`, `bottom_center` and
`bottom_right`. Clients keep the resulting window inside the usable display
area.

When the backend advertises `credential_store`, secrets are referenced by
credential IDs and managed through the capability-gated `credentials.*`
operations. Secrets are accepted only by `credentials.put`; they are never
returned inside responses, settings, events or diagnostics. The production
backend stores them in the desktop secret service rather than the settings
file.

## Independent implementation contract

GUI conformance:

- deserialize every response/event fixture;
- render all states and stable error codes;
- correlate out-of-order responses by `correlation_id`;
- recover from event sequence gaps with `state.get`;
- handle `conflict` by reloading settings;
- run entirely against a scripted `BackendClient` fake.

Backend conformance:

- validate every request fixture and return a correlated response;
- reject commands invalid for the current state;
- emit monotonically sequenced events;
- provide one terminal event per accepted session;
- enforce settings revisions and the 1 MiB frame limit;
- pass the same suite over in-memory and production transports.

## Change policy

Compatible v1 changes may add optional object fields or new capability-gated
message names. Removing/renaming fields, changing semantics, making optional
fields required or sending unnegotiated enum values requires a new protocol
version. A contract change is incomplete until this document, schema, fixtures,
Rust DTOs, fake backend and compatibility tests agree.
